# Local Test Control API

A dev/test surface for driving the E2E harness over HTTP. It is not a product
API, it is not started by the product, and it is not reachable from another
machine.

Implements the surface frozen in [`POST_MVP_TEST_PHASE.md`](../POST_MVP_TEST_PHASE.md)
against the contracts in `local_ai_stack.test_contracts`. HTTP lives in
`src/local_ai_stack/test_api/`; `test_application.py` composes it with the
controlled `StackTestHarness`. It adds no dependency: the server is
`http.server` from the standard library.

## Starting it

```
set PEPITOS_AI_HUB_TEST_TOKEN=<43+ characters>
python -m local_ai_stack.test_api --profile pepe
```

The token comes from `PEPITOS_AI_HUB_TEST_TOKEN`, or from a file named by
`PEPITOS_AI_HUB_TEST_TOKEN_FILE`. There is no default and no generated
fallback: without a token the server exits. The server command does not contain
the token as an argument, and startup output never prints it.

The server starts only through this explicit command or an explicit Python
`start()` call. The default harness mode is `controlled`, with a fresh ephemeral
world for each accepted run. Controlled provisioning can write fixtures inside
that run's root; importing or starting the API creates no harness root.

`--allow-network` and `--allow-gpu` permit the corresponding request flags;
without them such requests receive `403 not-enabled`. They do not replace the
controlled providers or enable real network/GPU workloads. `local-real` remains
unsupported: `--allow-real-providers` refuses startup, and a `local-real` HTTP
request is denied. The application also refuses it before allocating a world
if invoked directly. Configured roots are unsupported by this composition;
requesting one produces a failed run without allocating a root or accepting a path.

`--host` accepts a literal IPv4 loopback address and nothing else. `0.0.0.0`,
a LAN address, the name `localhost` and the IPv6 loopback `::1` are all refused
before a socket exists. There is no override. Remote use belongs behind an
authenticated tunnel that terminates on this machine.

`::1` is refused rather than supported because the server opens an IPv4 socket,
as the rest of the stack does. Approving an address the socket cannot open
would be worse than not offering the family at all, so the validator and the
socket agree on one family. Tests bind every approved address for real.

## Routes

All under `/internal/test/v1`, all requiring `Authorization: Bearer <token>`,
health included.

| Method and path | Purpose |
|---|---|
| `GET /health` | The server is up. |
| `GET /status` | Sanitized aggregate state plus this server's runs. |
| `POST /runs` | Validate a run request, queue it, return `202`. |
| `GET /runs/{run_id}` | Run state, the harness report, and stream diagnostics. |
| `GET /runs/{run_id}/events` | The run's events as SSE. |

There is no `/plan`, `/start`, `/stop`, `/services`, `/models` or `/cleanup`. A
phase is submitted as a one-phase run; a second command surface would duplicate
validation and create a second authority.

Unknown routes answer `404` — but only once authenticated. Without a token
every path answers `401`, so the surface cannot be enumerated.

## Requesting a run

```json
{
  "profile_id": "pepe",
  "phases": ["preflight", "plan"],
  "root_mode": "ephemeral",
  "provider_mode": "controlled",
  "allow_network": false,
  "allow_gpu": false
}
```

Those six fields are the whole vocabulary, and they mirror `TestRunSpec`
exactly. There is no field for a command, an executable, an argument list, a
working directory, an environment variable, a filesystem path, a URL, a port, a
PID or a service id, so a request cannot ask for any of them. Unknown fields
are rejected rather than ignored, as are unknown enum values, a profile the
server was not told about, and a repeated phase.

Bodies are capped at 4 KiB, must be `application/json`, and must carry a
`Content-Length`. A refused body is not read.

Only one run may be queued or running at a time; a second `POST /runs` answers
`409 run-in-progress`. Reading is not serialized: status and event streams are
served concurrently while a run is in flight.

## Run identifiers

A run id is 32 hexadecimal characters generated by the server. It is matched
against that exact pattern on the way in and is never joined to a path, so
there is nothing in it to traverse. Anything else is `404`.

## Events

Events are the harness's, not the API's. The server assigns storage, ordering
and fan-out; it does not rewrite what an event means.

- `id` is the sequence, starting at 1 and assigned by the store rather than
  trusted from the producer;
- `event` is the `TestEventKind` value;
- `data` is the whole serialized event;
- `Last-Event-ID` resumes after that sequence, and has to name a point the
  run actually reached;
- keep-alives are comment lines carrying no application state;
- exactly one `result` event ends a stream.

That last guarantee is the API's. If the harness emits a terminal event, it is
used. If the harness returns or raises without one, the server writes a
terminal event from the report so the stream always ends. Anything emitted
after the terminal event is dropped and counted in the run's diagnostics.

Retention is bounded: 32 runs, 512 events per run, 8 KiB of data per event.
Oversized event data is replaced by its size and long messages are truncated,
which is what keeps the stream from becoming a log dump.

A cursor outside the run's range is an error rather than silence, in both
directions. Below the buffer it answers `409 events-expired` instead of
skipping a gap. Above everything the run emitted it answers `409 events-ahead`
instead of an empty stream, which would tell a reader it was caught up on
events that never existed. The ceiling counts everything ever emitted, so
trimming the buffer never turns a valid cursor into a future one.

SSE is output only. There is no route that accepts a command over a stream.

## Stopping

`TestApi.stop()` stops accepting requests, then gives the timeout to whatever run is
in flight. A run is never interrupted: the harness owns whatever it started, so
cutting its thread down would leave a process, a file or a download half
finished with nobody left to complete it.

If the run is still going when the timeout expires, `stop()` raises
`ShutdownTimeout` rather than closing the socket and reporting a shutdown that
did not happen. The port stays bound, `address` keeps answering, and the server
keeps everything it needs, so calling `stop()` again once the run ends
completes the shutdown properly. What has already happened by then is that no
new request is accepted, so nothing else can start while it winds down.

There is no forced termination and no cancellation. See "Not in this round".

## Following a run

For example, after starting with `--profile pepe --port 8787`, use PowerShell
with the token already in the environment:

```powershell
$headers = @{ Authorization = "Bearer $env:PEPITOS_AI_HUB_TEST_TOKEN" }
$body = @{ profile_id = 'pepe'; phases = @('preflight', 'plan') } | ConvertTo-Json
$run = Invoke-RestMethod -Method Post -Uri 'http://127.0.0.1:8787/internal/test/v1/runs' -Headers $headers -ContentType 'application/json' -Body $body
$env:TEST_RUN_ID = $run.run_id
```

Read SSE using an environment-backed header, without putting the token in a
client command argument. Set `TEST_LAST_EVENT_ID` to the last received `id`
when reconnecting; the server resumes strictly after it.

```powershell
@'
import http.client, os
connection = http.client.HTTPConnection("127.0.0.1", 8787, timeout=30)
headers = {
    "Authorization": "Bearer " + os.environ["PEPITOS_AI_HUB_TEST_TOKEN"],
    "Last-Event-ID": os.environ.get("TEST_LAST_EVENT_ID", "0"),
}
try:
    connection.request("GET", "/internal/test/v1/runs/" + os.environ["TEST_RUN_ID"] + "/events", headers=headers)
    response = connection.getresponse()
    for line in response:
        print(line.decode(), end="", flush=True)
finally:
    connection.close()
'@ | python -
```

## What the API cannot do

Routes, scheduler and payload validation import `test_contracts` and one address
constant from `endpoints`, with no domain implementation imports. The sole
composition exception is `__main__.py` importing `create_test_api` from
`test_application.py`. That external module supplies a per-run harness factory
through the `TestHarness` protocol. HTTP does not become a service locator.
The API package still imports no `subprocess`, `psutil`, `shutil`, `ctypes`,
`winreg`, HTTP client or E2E implementation. AST tests enforce this boundary,
including the exact entry-point exception.

So the API cannot start a process, stop one, adopt an external one, write
configuration, download anything, or delete a model. It calls
`TestHarness.run` once per run and republishes what comes back. Ownership of
processes, paths, provisioning and runtime control stays where it already is.

## Status

`GET /status` reports the server, its run counts, the active run, and whatever
a `StatusSource` hands it under `system`, `gpu`, `services` and `models`. That
projection is sanitized here: filesystem paths and non-loopback URLs are
replaced, anything named like a secret is redacted, strings are truncated and
depth is capped. A loopback URL survives, because "where does this service
listen" is what status exists to answer.

The composed source is a detached snapshot of the last completed controlled run.
Before the first run these four keys are empty. It exposes controlled system/GPU
facts, service observations explicitly labelled `before_stop`, cleanup results,
and model resolution labelled `resolution-before-cleanup`. These are test-world
observations, not live facts about the user's machine or models surviving cleanup.
During a run the last completed snapshot remains available alongside `active_run`.
Reading status only copies this snapshot: it invokes no harness, scan, start,
stop, installation, configuration write or acquisition.

## Not in this round

- No cancellation. `TestRunState` is `queued`, `running`, `passed`, `failed`;
  a cancelled state would be a change to the frozen contract, so it is a
  `NEEDS_DECISION` rather than an invention.
- No local-real providers or kernel Win32 Job Object proof (P1/local-real).
- No configured-root selection or arbitrary paths through HTTP.
- Controlled provisioning installs Ollama only. Full offline model/config/smoke
  tests inject a server-side fixture catalog; the CLI uses shipped profiles and
  does not pretend that their real model weights were installed. See
  [the harness limits](e2e-harness.md) and [integration evidence](integration.md).
- No durable run store: restarting the API loses reports and replay history.
- No tunnel, no Tailscale, no SSH. Deliberately out of scope.
